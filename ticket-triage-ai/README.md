# ticket-triage-ai

Учебный проект классификации заявок службы поддержки. Система помогает диспетчеру выбрать подразделение и приоритет, показывает уверенность модели и сохраняет окончательное решение человека вместе с исходным прогнозом.

**Статус:** стартовая структура и документация. Модель, API и интерфейс ещё не реализованы; запуск приложения пока не предусмотрен. Реальных заявок, персональных данных и секретов в проекте нет.

## Участники и пользователи

Проект выполняет один участник, совмещающий роли аналитика, ML-инженера, разработчика, QA и менеджера проекта. В backlog роли обозначают вид работы, а не разных людей.

Пользователи продукта: диспетчер принимает решение по заявке; руководитель поддержки оценивает качество распределения и пропуски критических обращений.

## Данные и результат

По условию доступны 12 000 исторических заявок: ID, тема, текст, подразделение, приоритет. Сами данные пока не получены и не проверены. Модель использует тему и текст; подразделение и приоритет — две отдельные целевые метки. ID нужен для учёта, а не для обучения.

Рабочие классы приоритета: низкий, средний, высокий, критический. Это допущение заготовки: перед обучением сверить названия с исходными данными. Список подразделений также предстоит уточнить.

## MVP

1. Диспетчер вводит тему и текст заявки.
2. Система предлагает подразделение и приоритет с отдельной уверенностью для каждого прогноза.
3. Диспетчер подтверждает или изменяет любое из двух значений.
4. Система сохраняет исходный прогноз и итоговый выбор оператора, не перезаписывая одно другим.

Поиск похожих заявок и обнаружение дубликатов в интерфейсе отложены за пределы MVP.

## Критерии проверки

- Рассчитать Macro F1 и Weighted F1 отдельно для подразделения и приоритета.
- Macro F1 на тесте ≥ 0,72. Для заготовки проверяем обе задачи отдельно; уточнить область применения порога у преподавателя.
- Recall класса «критический» ≥ 0,80.
- Тест: 2 000 заявок, не участвовавших в обучении или подборе параметров.
- Ответ API для одной заявки ≤ 2 секунд; основной сценарий и обработка неверного ввода работают.

Это целевые критерии со слайда, а не достигнутые результаты. Для Weighted F1 порог не задан.

## С чего начать

1. Прочитать [схему данных](docs/data-schema.md) и [backlog](docs/backlog.md).
2. Уточнить классы приоритета и перечень подразделений.
3. Проверить обезличенную локальную выгрузку и подготовить отчёт по данным.
4. Перейти к простой базовой модели, затем к API и интерфейсу.

Инструкции по первому коммиту и публикации: [docs/git-setup.md](docs/git-setup.md).

В git допускаются только код, документация и искусственные примеры. `.gitignore` исключает локальные данные, модели, базы, логи и файлы окружения; содержимое остальных файлов нужно проверять перед коммитом.
