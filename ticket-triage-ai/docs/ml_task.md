# Постановка ML-задачи
**Ответственный:** один исполнитель ведёт постановку, подготовку данных, обучение, оценку и проверку интерфейса. Диспетчер утверждает каждую рекомендацию.

**Вход:** на момент регистрации доступны тема и текст. Они объединяются пробелом. ID нужен для проверки уникальности, разбиения и разбора ошибок. **Цели:** исторически назначенное подразделение и один из четырёх приоритетов — низкий, стандартный, высокий, критический. Каждая задача имеет один правильный класс на заявку и отдельный классификатор.

## Данные и протокол
Ожидаются 12 000 размеченных обращений. Имена подразделений поступают из данных. Проверяются схема, уникальность ID, метки и наличие хотя бы одного текстового поля. Проверяются классы в train, наличие критических примеров в validation и test, а также пересечение нормализованных текстов между частями. Семантические дубли и ошибки меток требуют отдельной проверки владельцем данных.

1. Сохранить выделенные 2 000 ID теста, при наличии использовать предоставленный список. При первом формировании — случайное разбиение со стратификацией по приоритету. Оставшиеся 10 000 разделить на 8 000 train и 2 000 validation с той же стратификацией. Seed 42. По подразделениям стратификация не выполняется.
2. Для каждой цели обучить на train наиболее частый класс и отдельный конвейер TF-IDF (униграммы и биграммы слов) с Logistic Regression. Сравнить C = 0.5 и 2.0 на validation, выбрать максимальный Macro F1. При равенстве для приоритета предпочесть больший recall критических, при полном равенстве — меньшее C.
3. Зафиксировать обе модели. Словарь, IDF и веса остаются обученными на train. После выбора оценить оба baseline на том же отложенном тесте. Использовать единый порядок меток для каждого сравнения.
4. Macro F1 усредняет F1 классов с одинаковым весом. Weighted F1 взвешивает их по числу истинных примеров. При неопределённом F1 класса используется 0. Для критических считать recall = TP / (TP + FN). По матрицам проверить число примеров каждого класса и направление ошибки.

## Условия проверки и разбор ошибок
Для принятия модели Macro F1 подразделения и Macro F1 приоритета должны **каждый** достигнуть 0,72, а recall критического приоритета — 0,80. Weighted F1 служит дополнительной характеристикой. Для редких классов рядом с оценкой нужно учитывать размер выборки.

Главный риск — критический запрос попадает в обычную очередь. Для каждого baseline отчёт показывает, сколько критических заявок получили каждую более низкую метку и в каких подразделениях это произошло. Для ручного разбора по сохранённым ID проверить пропущенные признаки срочности, неполный контекст и возможные ошибки разметки. Зафиксировать подтверждённые причины и число таких случаев. Содержательные выводы появятся после анализа реальных обращений. Повторная настройка по ошибкам теста требует свежей независимой выборки.

## Состояние проекта
Код и интерфейс проверяются синтетическим сценарием. Реальные распределения, ошибки, метрики и заключение о приёмке ожидают исторический CSV.
