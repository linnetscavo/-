# План оценки

Две задачи классификации: подразделение и приоритет. Базовый вариант для будущей реализации — TF-IDF по теме и тексту и отдельная логистическая регрессия для каждой задачи. Это предложение, код и обученные модели пока отсутствуют.

## Разделение данных

Из 12 000 записей по условию отложить 2 000 на финальный тест. Из оставшихся можно выделить 8 000 для обучения и 2 000 для валидации. Эти числа — план до проверки качества выгрузки. Если после очистки записей недостаточно, зафиксировать расхождение и согласовать разбиение.

Дубликаты и связанные обращения не должны попадать в разные части. Проверить распределения подразделений и приоритетов, особенно наличие критических заявок в тесте. Зафиксировать правила разбиения, seed и идентификаторы выборок локально. Обучать TF-IDF и модель только на обучающей части; параметры и пороги выбирать на валидации. Финальный тест не использовать для настройки.

## Отчёт и цели

| Метрика | Что показывает | Цель |
|---|---|---|
| Macro F1 | Среднее F1 классов с равным весом каждого класса | ≥ 0,72 на тесте |
| Weighted F1 | Среднее F1 с весами по числу примеров класса | Отчётное значение, порог не задан |
| Recall критических | Доля найденных критических среди всех действительно критических: TP / (TP + FN) | ≥ 0,80 |

Macro F1 и Weighted F1 считать отдельно для подразделения и приоритета. Слайд не уточняет, к какой задаче относится порог Macro F1; в заготовке предлагаем проверять его для обеих и уточнить это у преподавателя.

Дополнительно записать число примеров каждого класса, матрицы ошибок, размер теста, версии модели и данных. Если в тесте нет критических заявок, recall не определён и критерий не считается пройденным.

Для проверки времени ответа API записать оборудование, размер входа, число запросов и наличие прогрева. Цель со слайда — каждый измеренный запрос одной заявки занимает ≤ 2 секунд; отдельно сообщить максимум и среднее. Сейчас измерений и подтверждённых результатов нет.
