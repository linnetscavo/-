# Сценарий MVP
Диспетчер вводит тему и текст, получает две рекомендации с уверенностями, подтверждает или меняет каждую метку. Этот сценарий реализован консольной программой operator_cli.py. Графическая форма и HTTP API остаются запланированными.

Функция recommend сохраняет исходную рекомендацию до подтверждения. Функция resolve записывает обе итоговые метки одной транзакцией. После подтверждения повторная запись отклоняется, прогноз сохраняется отдельно. Пустой совокупный ввод и неизвестные метки отклоняются. Вероятности модели не калиброваны, финальное решение принимает человек.

SQLite в private/decisions.sqlite хранит id, created (UTC), mode, model_hash, proposal (JSON), final (JSON), resolved (UTC). Для каждой цели proposal содержит label и confidence. final содержит department и priority. Тексты заявок не сохраняются. После прерывания ввода рекомендация может остаться без финального решения.

В предыдущем практикуме JSON с ticket_id, model_version, prediction, operator_decision, decision_action и saved_at описывал предлагаемый контракт. Сохранённых записей этого формата в исходном репозитории нет. Текущая реализация использует перечисленные поля SQLite. Статус confirmed/changed определяется сравнением исходных и итоговых меток. Будущий API должен явно согласовать свой публичный контракт.

При сбое модели или базы консольный процесс завершится с ошибкой. Удобное сообщение и повтор сохранения без потери выбора предстоит добавить в графический интерфейс. Поиск похожих заявок, автоматическая маршрутизация и автоматическое переобучение отложены за пределы первого MVP.
