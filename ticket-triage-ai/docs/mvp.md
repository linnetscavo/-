# Сценарий MVP

Диспетчер вводит тему и текст, получает два прогноза с уверенностью, проверяет их, затем подтверждает или меняет подразделение и/или приоритет. При сохранении остаются обе версии решения.

Пустой ввод отклоняется понятным сообщением. При недоступности модели прогноз не выдумывается; пользователь видит ошибку и возможность повторить запрос. Низкая уверенность требует внимания оператора; числовой порог определить по валидационной выборке. Решение всегда подтверждает человек.

## Предлагаемое хранение решения

```json
{
  "ticket_id": "demo-001",
  "model_version": "demo-only",
  "prediction": {
    "department": "it_support",
    "department_confidence": 0.76,
    "priority": "medium",
    "priority_confidence": 0.64
  },
  "operator_decision": {
    "department": "it_support",
    "priority": "high"
  },
  "decision_action": "changed",
  "saved_at": "2026-11-03T10:00:00Z"
}
```

Пример искусственный; оценки уверенности придуманы для описания формата. Значения уверенности находятся в [0, 1]; это оценка модели, не гарантия правильности. `decision_action` равен `confirmed`, если обе метки совпали с прогнозом, иначе `changed`. `saved_at` — время сохранения в UTC.

Исходный прогноз и его версия не изменяются при правке оператора. Для MVP достаточно локального хранилища, исключённого из git. После сохранения и повторного чтения должны восстанавливаться обе версии. UI показывает успешное сохранение только после подтверждения хранилища; при ошибке предлагает повторить действие без потери выбора.

Поиск похожих заявок, автоматическая отправка заявки в подразделение и автоматическое переобучение по исправлениям не входят в первый MVP.
